## Анализ, идентификация проблем


### Потенциальные проблемы
- MES
  - перегружен, одновременно делает разные задачи 
    - выполняет оценку стоимости
    - рабочим инструментом для операторов и производства
    - участвует в цепочке создания заказа
  - один инстанс - плохо влияет на рост заказов
  - долгая загрузка дашбордов заказов
   
- CI/CD, QA
  - ручной деплой Release и Prod
  - ручные тесты E2E
    - задержка релиза

- связанность CRM и Shop
  - CRM обращается напрямую в базу данных Shop БД 

- Управление заказами
  - статусы заказа меняются о системы к системе (Shop-CRM-MES)
  - никто не несет ответственность за состояние заказа
  - нет контроля за последовательностью шагов заказа

- RabbitMQ без гарантированной доставки сообщений
  - нет возможности читать данные повторно 
    - судя по происходящему сбою заказов сервисы теряют сообщения, вследствие чего нарушается цепочка заказа


### Инициативы (в порядке приоритета)
- 1:
  - цель: внедрить единое управление статусов заказа
  - подход:
    - создать и внедрить новую систему централизованного управления заказа
    - использовать паттерн Saga (оркестрация "шагами" заказа)
  - обоснование:
    - явный корень проблемы компании, потеря прибыли из-за отсутствия управления заказами
    
- 2:
  - цель: разгрузка MES, разделение на сервисы
  - подход:
    - выделить сервис расчета стоимости
    - выделить сервис для операторов и операций производства
    - улучшение производительности дашбордов
  - обоснование:
    - причинно-следственные связи - долгая обработка стоимости и сбой работы для операторов и производства 
  
- 3:
  - цель: масштабирование ландшафта 
  - подход:
    - горизонтальное для MES, CRM, Shop
    - БД - репликация/кеширование/шардирование, разные инстансы для запросов чтения и записи
  - обоснование:
    - большой рост нагрузки за последние время + API для продавцов

-4:
  - цель: повышение надежности передачи сообщений между сервисами
  - подход:
    - стандартизировать события
    - реализовать обработку недоставленных событий
  - обоснование:
    - потеря статутов заказов при росте нагрузки 

- 5:
  - цель: ускорение деплоя
  - подход:
    - автоматизация тестирования
    - автоматизировать выкатку релизов и прод
  - обоснование:
    - долгое обновление вследствие чего накопление технического долга

- 6:
  - цель: усилить команду
  - подход:
    - нанять сильного React-разработчика (слабые текущие навыки)
    - нанять C# разработчика для ускорения реализаций инициатив по MES
    - нанять DevOps инженера - усилить автоматизацию CI/CD
  - обоснование:
    - наем по ситуации после приоритетных инициатив как усиление, ускорение их реализаций

### Целевая архитектура через полгода
- создана и интегрирован единая система управления заказами
- MES разделен на сервисы: для операторов и расчета стоимости
- "Общение" между сервисами стандартизированно, с полным контролем сообщений
- Дашборды "летают" за счет оптимизаций в чтении и агрегации данных
- Поставка деплоя настроена без задержек, большая часть тестов автоматизированна.

### Три пункта
- 1:
  - единая система управления заказами
    - корень зла и потеря прибыли на текущий момент
- 2:
  - разделение MES
    - техническое разделение тяжелого сервиса
- 3:
  - ускорение Дашборда и стандартизация данных между сервисами
    - полностью покрываем проблемы с цепочкой (управлением) заказов
