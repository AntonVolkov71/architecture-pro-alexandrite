## Мотивация (зачем вообще мониторинг и что это даст)
- обоснование:
  - компания узнает о проблемах из вне (от пользователей, операторы, продавцов) и поздно, когда уже произошло 
  - после анализа ландшафта выяснилось, что система "живет" с проблемами, которые растут как снежный ком
    - деградация, накопление ошибок
  - отсутствие контроля за системой, нет возможности определять источники проблем
  - развитие производства и направлений только ухудшает общее состояние системы 
    - усиливается нагрузка на систему
  - вследствие чего
    - потеря прибыли, потеря клиентов, репутационные риски

- цель мониторинга:
  - получить полный контроль над системой, включая
    - инфраструктуру, системы и бизнес-процессов
  - выявлять первопричины возникших проблем  
  - устранять ошибки до того, как они дойдут до пользователей
  - иметь основу для расширения бизнеса в технической области
    - ускорение рабочего процесса разработки - уменьшение времени на поиск и устранение ошибок
  - улучшить "настроение" пользователей, продавцов, операторов


## Выбор подхода к мониторингу
- для каждой предметной области системы необходимо применить комбинированный подход

- метод USE 
  - цель:
    - определить нагрузку на железки - процессора, памяти
    - занятость ресурса для масштабирования (сервис узкое горло или нет)
    - оценка производительности баз данных - дальнейшее решение для репликации/кеширования/шардирования
  - основные узлы: MES API, Shop API, CRM API, и БД Shop DB, MES DB 

- метод 4 золота от Гугла 
  - цель:
    - проверим активность пользователей, 
    - фиксация количества ошибок в запросах (удачные/неудачные)
  - основные узлы: MES API, Shop API, CRM API

- метод RED 
  - цель: MES API, Shop API
    - определим корректность ответов на запросы
    - фиксирование самих ошибок в бизнес-процессах

## Метрики
- метрики - показывают количество во времени
- ярлыки - покажут точно в каком месте для различия одной и той же метрики

- Шина данных (RabbitMQ)
  - Number of dead-letter-exchange letters in RabbitMQ (письма без ответа)
    - цель: обнаружение потерянных событий - заказы пропадают и не обрабатываются
    - ярлыки: 
      - queue, routing_key 
        - направления и пути в шине
      - consumer, producer 
        - какой сервис отправил и принял 
  - Number of message in flight in RabbitMQ (количество событий)
    - цель: определение перегружена ли шина данных
    - ярлыки:
      - queue - отрабатывают ли очереди
      - service - выделение сущности события

- Shop API
  - Number of requests (RPS) - (количество запросов)
    - цель: определение нагрузки (особенно возрастание)
    - ярлыки:
      - endpoint, http_method - ручка и тип запроса
  - Response time (latency) for shop API (время ответа на запрос)
    - цель: выявление задержек времени ответа
    - ярлыки:
      - endpoint, http_method - ручка и тип запроса
  - HTTP 200 / HTTP 500 (ошибочный или удачный ответ)
    - цель: корректность сервиса
    - ярлыки:
      - endpoint, http_method - ручка и тип запроса
  - CPU % / Memory utilisation (показатели процессора и RAM)
    - цель: определение нагрузки на железку, выявление узкого горлышка
    - ярлыки: - уже встроены (хост, сервис, то есть что за железяка и где она)

- CRM API
  -  Number of requests (RPS) - (количество запросов)
    - цель: определение нагрузки (особенно возрастание)
      - ярлыки:
        - endpoint, http_method - ручка и тип запроса
  - HTTP 200 / HTTP 500 (ошибочный или удачный ответ)
    - цель: корректность сервиса, выявление пропажи подтверждения заказов
    - ярлыки:
      - endpoint, http_method - ручка и тип запроса
  - CPU % / Memory utilisation (показатели процессора и RAM)
    - цель: определение нагрузки на железку, выявление узкого горлышка
    - ярлыки: - уже встроены (хост, сервис, то есть что за железяка и где она)

- MEs API
  - Number of requests (RPS) - (количество запросов)
    - цель: определение нагрузки от операторов
    - ярлыки:
      - endpoint, http_method - ручка и тип запроса
  -  Response time (latency) for shop API (время ответа на запрос)
    - цель: выявление проблем с дашбордами
      - ярлыки:
        - endpoint, http_method - ручка и тип запроса
  - CPU % / Memory utilisation (показатели процессора и RAM)
    - цель: определение нагрузки на железку, выявление перегрузки системы (особенно системы подсчета стоимотси)
    - ярлыки: - уже встроены (хост, сервис, то есть что за железяка и где она)

- Базы данных
  - Memory utilisation - использование оперативной памяти
    - цель: определение нагрузки как использование БД оперативной
    - ярлыки: - уже встроены
  - Number of connections (DB) - активные соединения к БД
    - цель: определение нужды для реплики, выявление повышенной нагрузки на БД
    - ярлыки: - уже встроены
  - Size of DB instance - размер на диске
    - цель: слежение за размером данных
    - ярлыки: - уже встроены

- Хранилтще S3
  - Size of DB instance - размер на диске
    - цель: слежение за размером данных
    - ярлыки: - уже встроены


## План действий
- Развернуть место куда складываем метрики
  - единое хранилище, для удобного анализа, что происходит с системой
- Настроить сбор ресурсных метрик (процессор, память)
  - понимание, где перегруз железок - понимать код или железо
  - для определения нужды в масштабировании
- Настроить сбор метрик бизнес-процессов в API
  - определение нагрузки на систему количественно
  - определение ошибок в бизнес-процессах
- Настройка сбора в шине данных
  - определение как, сколько и насколько ходят данные между сервисами
- Настройки дашбордов метрик
  - технические метрики - нагрузка инфрастуктур - железо
  - бизнес-метрики - количество новых заказов, время заказа
  - шина данных - количество очередей в RabbitMq, ошибки
  
## Показатели насыщенности
- CPU более 80% в течение 10 минут 
  - заканчивается запас ресурсов, предупреждения падения сервиса
- Number of message in flight более 100 (корректируем опытным путем)
  - количество запросов в работе, если растет где-то на каком этапе обработки произошел сбой
- Response time (latency)
  - количество быстрых ответов - выставляет бизнес (там всякие SLA, SLO, SLI) - например 95% доля быстрых
  - индикатор, что сервера перегружены
- HTTP 500 более 5% от всех запросов
  - при росте показателя начинается какая-то проблема
- Соединения к БД более 80% (так как с железом)
  - кончается запас ресурсов
